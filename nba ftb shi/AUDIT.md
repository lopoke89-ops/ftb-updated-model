## 🔴 CRITICAL ISSUES

### 1. The v3 output data is WRONG — players have garbage metrics

**File:** `output_v3/ftb_data_output_v3.json`

The original pipeline (`ftb_pipeline.py`) outputs **correct** data:
```
"Luka Doncic":     ftbMade: 16, gamesStarted: 65, firstShotRate: 0.2462
"Anthony Edwards": ftbMade: 20, gamesStarted: 66, firstShotRate: 0.303
```

The v3 processor outputs **broken** data:
```
"Q. Post":     ftbMade: 9,  gamesStarted: 9,  firstShotRate: 1.0
"D. Clingan":  ftbMade: 11, gamesStarted: 11, firstShotRate: 1.0
"D. Robinson": ftbMade: 9,  gamesStarted: 9,  firstShotRate: 1.0
```

**Root causes:**
- **`gamesStarted` is set to `ftb_made`** — line 297 of `optimized_data_processor.py` does `games_started = max(unique_games, self.config.min_games_started)` but `unique_games` = number of games the player *scored a first basket in*, NOT total games started. Every player with ≥3 FTBs gets `firstShotRate = 1.0`.
- **Player names are abbreviated** (e.g. "Q. Post", "D. Clingan") instead of resolved to full names. The original pipeline resolves "D. Clingan" → "Donovan Clingan" via fuzzy roster matching. The v3 processor does NO name resolution — it just takes raw Excel names as-is.
- **Shot counts are inflated** — the `_calculate_shot_distribution` method processes BOTH home and away shot descriptions for every player row, even when a player only appears on one side. A player who scored at home gets their home shot counted PLUS whatever unrelated away shot description is on that row.

### 2. Every player without a roster entry gets position "SF"

**File:** `optimized_data_processor.py`, line 356

The v3 processor falls back to "SF" for any player not found in roster. Since it uses abbreviated names (e.g. "D. Clingan") but the roster stores full names ("Donovan Clingan"), **most players fail roster lookup** and get tagged as SF.

Spot-check from the output:
```
"D. Clingan": position: "SF"   ← Actually a Center
"Q. Post":    position: "SF"   ← Actually a Center (Quentin Post)
```

The original pipeline has a multi-strategy name resolver (`resolve_player`) with accent stripping, abbreviated→full matching, last-name fuzzy matching, and team disambiguation. The v3 processor has NONE of this.

### 3. All grades are identical — grading algorithm is flat

Every player in the v3 output gets grade `"B-"` with probability ~0.68. This is because:
- `firstShotRate` is 1.0 for everyone (bug #1)
- The normalization in `_normalize_score` compresses all values to the same narrow band
- `_calculate_position_score` returns tiny values (~0.1-0.2) since it multiplies weight × (shots/total) which are small fractions
- Net result: composite score ≈ 0.65-0.69 for all players → everyone gets B-

**The grading system produces zero differentiation.**

### 4. The "optimized" HTML is NOT a replacement for the production app

**File:** `ftb-scout-optimized.html` (820 lines) vs `ftb-scout.html` (7,012 lines)

The optimized HTML is missing **all** of the following features from the production app:
- Live ESPN schedule fetching and game selection
- Roster synchronization with ESPN/balldontlie APIs
- Injury data integration
- Play-by-play fetching and analysis
- JEDIBETS data engine
- Parlay builder with sportsbook rules
- Position likelihood scoring
- Team stats panel
- Odds display
- Multi-tab interface (Picks, Engine, Teams, Roster Sync)
- Google Fonts loading
- The entire `SEASON_FTB_DATA` constant with 200+ players
- The `FALLBACK_POSITION_FTB` data

It's a basic search/filter/sort card list. It cannot replace the production app.

### 5. The optimized HTML can't even load its own data

**File:** `ftb-scout-optimized.html`, line 532

It tries to fetch `./output_v3/ftb_data_output_v3.json` via `fetch()`. This fails when opened as a local `file://` URL (which is how the user runs these HTML files) because `fetch()` doesn't work with `file://` protocol in most browsers. The production app avoids this by embedding data directly in the HTML via `SEASON_FTB_DATA`.

### 6. `ftb_engine_v3.py` `export_results()` function is broken

**File:** `ftb_engine_v3.py`, lines 530-557

```python
for team, players in engine.player_metrics.items():
    game_id = f"{team}_{datetime.now().strftime('%Y%m%d')}"
    if game_id not in games_data:
        games_data[game_id] = []
    games_data[game_id].append(players)
```

`engine.player_metrics` is `Dict[str, PlayerMetrics]` (keyed by player name, values are PlayerMetrics objects). The code iterates it as if it's `Dict[str, List[PlayerMetrics]]` (keyed by team). It would append individual `PlayerMetrics` objects (not lists) with game IDs based on player names. This function would crash or produce nonsense if called.

### 7. `process_play_by_play()` is never actually called

**File:** `ftb_engine_v3.py`, lines 199-224

The entire PbP processing pipeline in the engine is dead code. No caller ever invokes it. The `optimized_data_processor.py` reads directly from Excel and processes rows itself — it never converts them to PbP format or passes them through the engine's PbP processor.

## ⚠️ MEDIUM ISSUES

### 8. `config_v3.json` is never loaded

The config file exists but nothing reads it. `optimized_data_processor.py` hard-codes its own `ProcessingConfig` dataclass. The grading weights, position weights, cache settings, and parlay constraints in `config_v3.json` are all ignored.

### 9. `requirements_v3.txt` lists packages that aren't used

- `fastapi`, `uvicorn` — no API server exists
- `pydantic`, `marshmallow` — not imported anywhere
- `sqlalchemy`, `sqlite3` — no database code
- `structlog`, `prometheus-client` — not used
- `memory-profiler` — not used
- `aiohttp` — not used

Only `pandas`, `openpyxl`, and standard library modules are actually needed.

### 10. Cache deserialization silently produces wrong objects

**File:** `optimized_data_processor.py`, lines 430-434

When loading from cache, it does `PlayerMetrics(**metrics)` where `metrics` came from `_serialize_player()`. But `_serialize_player` outputs keys like `"ftb_made"`, `"first_shot_rate"`, etc. — which happen to match the dataclass field names, so it works. BUT if the cache was saved with the `asdict()` approach (which was the original code before fixes), the key names could differ and silently produce wrong objects.

### 11. Team metrics are mostly placeholder values

**File:** `optimized_data_processor.py`, lines 409-422

Every team gets identical placeholder data:
```python
position_vulnerability = {"PG": 0.2, "SG": 0.2, "SF": 0.2, "PF": 0.2, "C": 0.2}
pace_factor = 1.0
offensive_efficiency = 1.0
```

The original pipeline (`ftb_pipeline.py`) actually computes real tip win %, first FG %, and position-vs-defending-team breakdowns from the data. The v3 processor throws all of that away and returns constants.

### 12. `tip_win_pct` calculation is wrong

**File:** `optimized_data_processor.py`, line 395

```python
tip_wins = len(home_games)  # Assume home team wins tip (placeholder)
tip_win_pct = tip_wins / total_games
```

This just returns the percentage of games where the team played at home. It has nothing to do with tip-offs. The original pipeline at least uses clock comparison (who scored first = higher clock value) as a proxy.

### 13. Parlay data uses team abbreviations as game IDs

**File:** `optimized_data_processor.py`, line 589

```python
parlay_data = self.engine.generate_parlay_data(team_players)
```

`team_players` is keyed by team abbreviation (e.g., "LAL", "BOS"). These become the `game_id` values in parlay output. Real game IDs should represent matchups (e.g., "LAL_vs_BOS_20260312"). This means the parlay data has no concept of which teams are actually playing each other.

### 14. `_calculate_consistency` measures the WRONG thing

**File:** `ftb_engine_v3.py`, lines 365-378

It calculates variance of shot type distribution and calls low variance "consistent." But a player who scores 100% via layups has LOW variance (very consistent method) while a player who uses all shot types equally has HIGH variance. The current formula rewards players who are *diversified* shooters, not *consistent* first-basket scorers. For FTB analysis, you actually want to know: "does this player reliably score first baskets game after game?" — which requires game-level data, not shot type spread.

## 🎯 HONEST ASSESSMENT

The three new "v3" files (`ftb_engine_v3.py`, `optimized_data_processor.py`, `ftb-scout-optimized.html`) are **not production-ready** and should **not replace** the existing working system. Specifically:

1. **The v3 data output is worse than v2** — wrong player names, wrong games started, wrong shot counts, flat grades
2. **The v3 HTML is a downgrade** — missing 90% of the production app's features
3. **The v3 engine has dead code** — PbP processor is never called, `export_results` is broken
4. **Config and requirements files are aspirational** — they describe a system that doesn't exist yet

### What should actually happen next

1. **Keep using `ftb_pipeline.py` and `ftb-scout.html`** — they work
2. **Port the v2 pipeline's name resolution** into any v3 work (fuzzy matching, accent stripping)
3. **Fix `gamesStarted`** — use team total games, not player FTB count
4. **Fix shot distribution counting** — only count the side (home/away) the player actually scored on
5. **Build grading on top of existing correct data** rather than reprocessing from scratch with bugs
6. **Integrate new features (grading, parlay prep) INTO the existing app** rather than building a new stripped-down app
7. **Delete `config_v3.json`, `requirements_v3.txt`** — they describe unused infrastructure
8. **Clean up redundant HTML copies** (`ftb-scout v10.html`, `ftb-scout_fixed.html`)
